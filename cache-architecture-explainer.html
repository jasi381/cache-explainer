Cache Architecture: First Principles

Welcome to this highly interactive system-design teaching tool. You are going to learn caching architectures by visually following data as it moves through a system.

A cache is a high-speed data storage layer which stores a subset of data, typically transient in nature, so that future requests for that data are served up faster than is possible by accessing the data's primary storage location. Caching allows you to efficiently reuse previously retrieved or computed data.

B. Basic Architecture

In a standard web architecture, requests flow from a Client to a Server, which queries a Database. A Cache is introduced to intercept or optimize these requests. Click on the components below to understand their responsibilities.

C. Where Can Caching Exist?

Caching does not just live in a single "Redis node". It can exist at almost every layer of an architecture:

Location Description Examples
Client-Side The browser or mobile app stores data locally to avoid network requests entirely. Browser HTTP Cache, Service Workers, LocalStorage
Edge / CDN Geographically distributed servers cache static assets closer to users. Cloudflare, AWS CloudFront
Local Cache In-memory caching residing on the application server itself (Decentralized). Very fast, but suffers from inconsistency across multiple servers. Guava, ConcurrentHashMap, Memcached (local)
Distributed Cache A standalone caching tier shared by all application servers (Centralized). Solves local cache inconsistency. Redis, Memcached

E. Read Patterns

How does the application interact with the cache when reading data? There are two dominant patterns: Cache-Aside and Read-Through.

1. Cache-Aside (Lazy Loading)

The application is entirely responsible for querying the cache, and if missing, querying the database and explicitly populating the cache.

2. Read-Through

The application treats the cache as the main data store. If there is a miss, the cache layer itself is responsible for fetching the data from the database and returning it.

Side-by-Side Comparison

Feature Cache-Aside Read-Through
Responsibility Application code handles DB fallback Cache abstraction handles DB fallback
Application Complexity Higher (requires checking cache, then DB, then setting cache) Lower (just asks the cache for data)
Cache Awareness App is aware of both Cache and DB App is only aware of Cache layer

F. Write Patterns

When data is updated, how do we keep the cache and database in sync? The strategy you choose drastically impacts performance and consistency.

1. Write-Around

Data is written directly to the database, bypassing the cache. The cache entry is invalidated. This prevents "cache pollution" for data that is written but rarely read.

2. Write-Through

Data is written into the cache and the database synchronously. The client doesn't get a success response until both are updated. Guarantees consistency but increases write latency.

3. Write-Back (Write-Behind)

Data is written to the cache alone, and the client receives immediate success. The cache asynchronously persists the data to the database later. Extremely fast, but risks data loss if the cache crashes before syncing.

Write Pattern Comparison

Pattern Cache Updated DB Updated Sync / Async Write Latency Data Loss Risk
Write-Around No (Invalidated) Yes Sync Medium Low
Write-Through Yes Yes Sync High Low
Write-Back Yes Later Async Very Low High

H. Cache Eviction & TTL

Do not confuse invalidation with eviction.
- Invalidation happens when data becomes incorrect/stale.
- Eviction happens when the cache runs out of space.

Eviction Policy: LRU (Least Recently Used)

When capacity is reached, the item that hasn't been accessed for the longest time is removed.

TTL (Time To Live)

TTL is an expiration mechanism. Data is automatically removed after a set time to prevent it from becoming indefinitely stale, regardless of capacity.

K. Failure Scenarios

What happens when things break? A robust system degrades gracefully.


L. Cache is NOT the Source of Truth

Unless intentionally designed as a durable primary store, you must mentally separate the roles:

DATABASE

Persistent.
Source of Truth.
Durability is priority.

CACHE

Transient.
Performance Layer.
Speed is priority.

Note: Write-back architectures temporarily violate this by holding the authoritative state in the cache until asynchronous persistence completes, increasing data-loss risk.

M. Real-World Example Walkthrough

Scenario: E-Commerce GET /products/123

Using Node.js (API), Redis (Cache), and PostgreSQL (Database).

  1. First request: Client hits API. API queries Redis. Redis returns MISS. API queries PostgreSQL. Data returned. API sets data in Redis. API returns response to Client.
  2. Second request: Client hits API. API queries Redis. Redis returns HIT. API returns response instantly. PostgreSQL is bypassed.
  3. Admin updates price: Admin Dashboard updates PostgreSQL directly. Dashboard sends an INVALIDATE command to Redis for key product:123.
  4. Next request: Client hits API. Redis returns MISS. API queries PostgreSQL to get the new price. API caches new price. API returns response.

WRITE PATH:
Client -> Server -> ┌────────────────────────────────────────────────────────┐
                    │ Write-Around  -> Database -> Invalidate Cache          │
                    │ Write-Through -> Update Cache & Database Synchronously │
                    │ Write-Back    -> Update Cache -> Database Asynchronously│
                    └────────────────────────────────────────────────────────┘

LIFECYCLE MANAGEMENT:
- Invalidation : Source data changed, explicitly remove/update cache entry.
- Eviction     : Cache is full, remove based on policy (LRU, LFU, FIFO).
- TTL          : Time limit reached, entry naturally expires.
